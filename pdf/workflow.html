RHU LabChain / Workflow guide

From patient registration
to verified laboratory report

A practical map of the hybrid laboratory record system: who acts, what happens next, and when a result becomes available.

Scope: Phase One academic prototype. This guide describes the repository implementation and its documented operating modes. Use synthetic or formally de-identified records.
1
Register patientRegistration / CashierCreate or locate the patient record; link a patient login when portal access is needed.
2
Consult and requestDoctorRecord the consultation and create the laboratory request with selected tests or panels.
3
Classify paymentRegistration / CashierRecord Paid, Free, Waived, or Subsidized before specimen accession.
4
Handle specimenLaboratory StaffAssign accession/specimen identifiers, collect the sample, and record receipt or rejection.
5
Test and check qualityLaboratory StaffEnter results, record quality control (QC), and resolve repeats or referrals before submission.
6
Submit and approveStaff → SupervisorSubmit a result version. A different authorized user reviews and approves, or rejects with a reason.
7
Store and registerAutomated servicesEncrypt the approved snapshot, store the package, and register its proof. Save both receipts.
8
Release reportLaboratory SupervisorRelease the registered version. The ledger release receipt enables the report and verification URL.
9
Review, access, verifyDoctor / Patient / PublicThe doctor records review; the patient sees their released results; QR verification shows redacted proof.

Read from top to bottom. Exception paths return work for correction or hold publication until a failed step is resolved.

Normal order status sequence

REQUESTED → PAYMENT_CLASSIFIED → ACCESSIONED → COLLECTED → IN_TESTING → FOR_VERIFICATION → APPROVED → STORAGE_PENDING → STORED → LEDGER_PENDING → LEDGER_REGISTERED → RELEASED
Before submissionAll required test items need a passing QC attempt or an incorporated referral result. Required repeats must be resolved.
Before releaseThe result version must be VERIFIED and its publication status REGISTERED. An initial order must be LEDGER_REGISTERED.
Status distinction: order status, result-version status, and publication status are separate. The UI can show an approved order as “Completed” while storage or ledger work is still pending. Only release makes it available as a released result.

Access starts with authentication and role checks. Seed accounts must complete their required password change before protected workflows.

Service workflow

How approval becomes a public proof

The browser reaches four services through the gateway. Authentication owns identity and sessions; Records & Sync coordinates the laboratory workflow. Each service owns its data.

1. Records & Sync: approve the immutable versionCommit approval, audit/history, and a STORE_APPROVED_RESULT outbox event. Build the canonical result snapshot.
↓
2. Encrypted Storage: protect and store the snapshotCreate an AES-256-GCM package with a fresh data key and nonce. Store the encrypted envelope in private IPFS, or the labeled filesystem adapter.
↓
3. Records & Sync: save the storage receiptRetain the ciphertext hash and protected object reference for the exact record/version, then enqueue REGISTER_LEDGER.
↓
4. Verification: register proof and return a receiptRegister opaque record/version and integrity metadata through Fabric Gateway, or the labeled file ledger. Records advances to LEDGER_REGISTERED.
↓
5. Supervisor + services: release the registered versionThe supervisor requests release. Verification records the ledger release and issues an opaque token and URL; Records saves the receipt and marks the version RELEASED.
↓
6. Separate access paths: private report and public verificationAuthorized doctors and the linked patient access the released report. /verify/<opaque-token> checks token validity and the registered proof.

What the public verifier sees

Verification status, opaque record identifier, version, issuing organization, approval/release timestamps, and ledger label. Patient identity, test names and values, notes, CIDs, and keys are excluded. This is a proof/status check; it does not independently validate clinical accuracy or an uploaded report file.

Native developmentFile-backed data, encrypted filesystem objects, and a simulated file ledger.
Docker / FabricBase Docker uses MySQL and private Kubo. Fabric needs its separate bootstrap; check readiness for fabric and simulated: false.

Exceptions and traceability

When the normal flow pauses

Rejected specimenRecord the rejection reason. The order can enter RECOLLECTION_REQUIRED, then return to accession for a new specimen. Do not advance the rejected sample into testing.
QC failure, repeat testing, or referralKeep the result in laboratory work until required QC passes or an external referral result is incorporated. Resolve the required repeat before submitting.
Supervisor rejectionKeep the rejected version and reason, and create a linked draft. For the initial workflow the order returns to IN_TESTING; the next version needs verification again.
Correction after approval or releaseCreate a linked new version; repeat QC/submission, approval, storage, registration, and release. Releasing a correction marks the prior released version SUPERSEDED in Records. Do not assume that this automatically revokes an older public token.
Storage, ledger, or release failureKeep the failed step visible in the outbox. Retries reuse the event idempotency key. The current handler uses increasing delays, capped at one hour, and changes to FAILED_REVIEW after ten failed attempts.
Connection loss or synchronization conflictSupported drafts and queued commands use IndexedDB. Reconnect and synchronize; review duplicate or revision-conflict receipts. Approval and release require current online server state. Offline synchronization remains a prototype capability.
Invalid, expired, or revoked QR tokenShow the verification outcome without exposing patient information. A failed lookup must not be presented as a verified report.
